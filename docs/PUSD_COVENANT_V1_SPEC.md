# PUSD covenant v1 — prototype specification

Status: **experimental, unreviewed, not deployable**.

This design is isolated from `AjoCircleV2.cash`. PUSD is a CashToken category distinct from the circle's state/receipt category, so the PUSD pool cannot be assumed to share a UTXO with the circle state NFT. CashTokens outputs carry one category each. The prototype uses separate state, member-receipt and PUSD-pool UTXOs under one covenant locking bytecode.

## Asset identity and units

- PUSD mainnet category ID (issuer-published): `2469acc5afa4b10cb5b5c04afb89c3a3ffd61c5da9c01e26d00951cae2a02544`.
- Contract parameters must receive the category in CashScript's introspection byte order (reverse the displayed wallet/explorer ID before constructing the contract).
- Fungible amounts are integers in raw CashToken units. The UI currently uses a 2-decimal display convention; the contract does not use floating point.
- Token category alone is not enough for wallet UI identity; every UTXO and signed transaction must be checked against the full category and expected amount.

## UTXO model

All three covenant UTXOs use the same PUSD-aware contract locking bytecode, but distinct token categories:

| Position | Role | Token category |
|---|---|---|
| Input/output 0 | Circle state NFT | circle category, minting capability |
| Input/output 1 | One member receipt NFT | circle category, immutable |
| Input/output 2 | PUSD pool | PUSD category, fungible amount |

The receipt commitment is `0x52 || memberIndex(1 byte) || credit(8 bytes)`.
The state commitment is `0x53 || round(1 byte)`; `0x54` marks a completed rotation.

### Add credit

Inputs: state NFT, one member receipt, PUSD pool, member PUSD funding UTXO.

Outputs: updated state NFT (unchanged), updated member receipt, PUSD pool increased by exactly the credited token amount, optional member PUSD change, and only token-free BCH change.

The wallet-side planner must separately prove the PUSD funding UTXO belongs to the member and contains no unexpected NFT. CashScript's introspection has an empty-NFT ambiguity for some CashToken UTXOs, so the transaction verifier must inspect full prevout token metadata and reject unexpected NFTs before signing.

### Payout

Inputs: state NFT, every member receipt in index order, and PUSD pool.

Outputs: state advanced (or terminal marker), each receipt reduced by exactly one round contribution, PUSD pool reduced by exactly `memberCount × contribution`, and exactly one PUSD output to the scheduled member. Any other output must be token-free and explicitly accounted for as BCH change/fees.

The current contract file is an experimental covenant prototype. The contribution path includes an explicit BCH fee input and returns token change; the payout path funds the recipient's 1,000-sat CashToken carrier from the pool UTXO and bounds the BCH fee. These rules still require transaction-level tests and independent review. The prototype also needs a genesis/setup flow for state and receipt NFTs, exhaustive treatment of all token/NFT edge cases, and end-to-end tests with real CashTokens transactions. Do not create a contract address from it or use it to lock funds.

## Required gates before deployment

1. Fix and compile the contract with CashScript 0.14; inspect generated bytecode and size.
2. Add a genesis/setup covenant that mints exactly one state NFT and one receipt NFT per registered member, with no extra minting outputs.
3. Specify a fee/carrier policy that cannot spend member BCH or PUSD unintentionally; check transaction-wide input/output value conservation.
4. Reject all unexpected token categories, NFT capabilities and commitments in every input and output, including the empty-NFT edge case.
5. Verify PUSD category byte order and UTXO metadata against independent mainnet sources.
6. Add transaction-builder and covenant integration tests for exact contribution, partial amount, token change, payout, depleted pool, wrong category, extra token output, NFT injection, wrong member, wrong receipt, duplicate input and fee manipulation.
7. Independently audit the covenant and raw signed transaction verifier.
8. Only then consider enabling the PUSD mainnet flow. Mainnet broadcast remains disabled.
